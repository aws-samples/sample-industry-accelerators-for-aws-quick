# Scientific Computing Sandbox

Per-user Python and bash sandboxes for AWS Quick, with scientific packages
pre-installed and no internet access. AWS Quick's own code environment cannot
install third-party packages. This accelerator runs code in Amazon Bedrock
AgentCore Runtime microVMs instead, behind an AgentCore Gateway that AWS Quick
connects to as an MCP server.

## Overview

The accelerator deploys seven sandbox **environments**: general data work,
cheminformatics, medical imaging, variant files, bulk RNA-seq, multi-omics,
and single-cell analysis. Each environment is its own container image and
AgentCore Runtime. AWS Quick calls `list_environments` to see what each one
contains, then passes the chosen environment to the other tools.

Each user gets one sandbox per environment, keyed to the verified `sub` claim
of their access token. Files under `/workspace` and background jobs persist
between tool calls and across the user's conversations, until the sandbox has
been idle for an hour (default), reaches its 8-hour maximum lifetime, or the
user resets it.

### Tools

| Tool in AWS Quick | What it does | Declared behavior |
| --- | --- | --- |
| `sandbox___list_environments` | Lists every environment with its packages (version, import name, purpose), programs, use cases and notes. With `environment`, also every installed distribution and version. Starts no sandbox | read-only |
| `sandbox___get_sandbox_info` | Environment, installed package versions, CPUs, memory, free disk, files in `/workspace`, running jobs, limits, `sandbox_instance`, a digest of the session ID, microVM uptime | read-only |
| `sandbox___execute_code` | Runs Python (the environment's virtual environment) or bash. Returns `status`, `exit_code` and the tails of `stdout` and `stderr`. With `background=true`, returns a `job_id` | write, destructive |
| `sandbox___get_job` | Status and output of a background job, optionally waiting up to 600 s. Lists jobs without `job_id` | read-only |
| `sandbox___cancel_job` | Kills a job's process group | write, destructive |
| `sandbox___read_file` | Reads up to 1 MiB per call, as text or base64, with `offset` paging | read-only |
| `sandbox___write_file` | Writes up to 1 MiB of text or base64 per call, optionally appending | write, destructive |
| `sandbox___list_files` | Lists a directory, optionally recursively (at most 5,000 entries) | read-only |
| `sandbox___reset_sandbox` | Stops the caller's sandbox in one environment, discarding its files and jobs | write, destructive |

Every tool except `list_environments` takes a required `environment`
argument. Its description lists each environment's ID, title and main
packages, so the model can often choose without calling `list_environments`
first.

The sandbox server declares the MCP annotations in the last column, but
AgentCore Gateway Lambda targets cannot carry annotations, so AWS Quick treats
every tool as write-capable. Gateway inline tool schemas also support only
`type`, `description`, `properties`, `required` and `items`. Bounds, allowed
values and defaults are stated in the descriptions and enforced by the
sandbox server.

Limits: code up to 256 KiB per call; synchronous timeout 1-600 s (default
300 s); output tails up to 256 KiB per stream (default 64 KiB); 8 running jobs
and 256 retained jobs per sandbox. Errors come back as
`{"status": "error", "error_code": ..., "message": ...}` with a fixed code
(`INVALID_INPUT`, `FILE_NOT_FOUND`, `NOT_TEXT`, `PERMISSION_DENIED`,
`JOB_NOT_FOUND`, `TOO_MANY_JOBS`, `UNAUTHENTICATED`, `UNKNOWN_TOOL`,
`THROTTLED`, `SANDBOX_UNAVAILABLE`, `SANDBOX_ERROR`, `INTERNAL_ERROR`). Error
messages never echo paths, code or exception text.

## Architecture

```text
AWS Quick ──(OAuth sign-in)──▶ your identity provider
    │
    │ MCP over HTTPS, JWT access token
    ▼
AgentCore Gateway ──▶ REQUEST interceptor (Lambda): verifies the token again,
(CUSTOM_JWT)          sets a caller header to the verified sub
    │
    │ target "sandbox"
    ▼
┌──────────────── isolated VPC (no internet gateway, NAT or default route) ────────────────┐
│ sandbox tools Lambda ──(InvokeAgentRuntime, runtimeSessionId = sha256(env, sub))──┐       │
│   list_environments from the bundled catalog                                      │       │
│   reset_sandbox = StopRuntimeSession                                              ▼       │
│                                     AgentCore Runtime per environment, one microVM       │
│                                     per session: the sandbox MCP server, /workspace      │
│ VPC endpoints: AgentCore, ECR API, ECR Docker, CloudWatch Logs, S3 (gateway)             │
│ DNS Firewall: only amazonaws.com and VPC-internal names resolve                          │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

| Stack | Resources |
| --- | --- |
| `<projectName>-Network` | The isolated VPC: two subnets placed by AgentCore-supported Availability Zone ID with no route out; ECR API, ECR Docker and CloudWatch Logs interface endpoints and an S3 gateway endpoint, each with a restrictive policy; security groups; Route 53 Resolver DNS Firewall; flow logs of rejected traffic |
| `<projectName>-Runtime` | Per environment: the container image asset, an AgentCore Runtime (MCP protocol, platform version V1, IAM inbound authorization, VPC network mode, idle timeout and maximum lifetime), its execution role, and a `<Environment>RuntimeArn` output |
| `<projectName>-Gateway` | The AgentCore Gateway (MCP, `CUSTOM_JWT` authorizer, REQUEST interceptor) with one Lambda target, the interceptor and sandbox tools Lambdas (Node.js 24, arm64), the AgentCore interface endpoint, the runtime resource policies, the Gateway role, and the `GatewayUrl` output |

### How a sandbox works

- **One sandbox per user and environment.** The interceptor verifies each
  caller's access token with the same settings as the Gateway authorizer and
  sets the token's `sub` in a caller header, overwriting any value the client
  sent. The sandbox tools Lambda reads that header, checks the `environment`
  argument against the deployed environments, and calls that environment's
  Runtime with `runtimeSessionId = sha256("code-sandbox:v1:<env>:<sub>")`.
  AgentCore Runtime runs each session in its own microVM (2 vCPU, 8 GB), so
  every call by the same user in the same environment reaches the same
  microVM.
- **Why sessions are keyed to the user.** AWS Quick starts a new MCP session
  for every tool call, so Gateway MCP sessions cannot keep a sandbox for a
  conversation. Deriving the Runtime session from the verified `sub` needs no
  state store. The trade-off is that a user's concurrent conversations share
  one sandbox per environment; the skill tells the model to work in a
  directory named for each task.
- **Lifetime.** A sandbox ends after the idle timeout (default 1 hour without
  calls), at the maximum lifetime (default 8 hours), or on `reset_sandbox`.
  The next call starts a new microVM with an empty `/workspace`, and
  `get_sandbox_info` reports a new `sandbox_instance`.
- **Background jobs** keep a sandbox alive: while a job runs, `/ping` returns
  `HealthyBusy`, so the Runtime does not stop the microVM as idle. The maximum
  lifetime still applies.
- **Each `execute_code` call is a fresh process.** No interpreter state
  survives between calls; state lives in files. Synchronous calls wait up to
  600 seconds; longer work uses `background=true` and `get_job`.
- **Environments are separate sandboxes.** A user's microVM for an environment
  starts only when they first use it, and environments share no files. Move
  results between environments with `read_file` and `write_file`.

### Network isolation

The network follows pattern 4 (an isolated VPC) of
[Network connectivity patterns for agents deployed on Amazon Bedrock AgentCore Runtime](https://aws.amazon.com/blogs/networking-and-content-delivery/network-connectivity-patterns-for-agents-deployed-on-amazon-bedrock-agentcore-runtime/),
with two additions for a sandbox that runs arbitrary code:

- **No way out.** Two isolated subnets with no internet gateway, NAT gateway,
  default route, peering or VPN. The runtimes use VPC network mode in these
  subnets, and the tools Lambda runs there too.
- **Only the endpoints the platform needs**, each with a policy. The S3
  gateway endpoint allows only `s3:GetObject` on the Region's ECR image layer
  bucket. The ECR and CloudWatch Logs endpoints admit only principals of this
  account (`aws:PrincipalAccount`) and only image-pull or log-writing actions.
  The AgentCore endpoint admits only the tools Lambda role, for
  `InvokeAgentRuntime` and `StopRuntimeSession` on these runtimes. Without
  these policies, code holding another account's credentials could send data
  out through the endpoints.
- **Security groups** allow the runtimes HTTPS only to the endpoints and the
  S3 prefix list, and the tools Lambda HTTPS only to the AgentCore endpoint.
  Nothing can connect to the runtimes. The VPC's default security group has
  no rules.
- **DNS Firewall.** Security groups do not apply to the VPC resolver, which
  would otherwise resolve any public name and let code send data out in DNS
  lookups. A Route 53 Resolver DNS Firewall rule group answers only
  `amazonaws.com`, its subdomains and VPC-internal names (`*.compute.internal`,
  `*.ec2.internal`), and answers everything else with `NXDOMAIN`.
- **Flow logs** of rejected traffic go to a CloudWatch log group with 30-day
  retention.

What this means for users: code cannot download data, call web APIs (PubChem,
ChEMBL, MyGene.info, Enrichr, Ensembl), fetch example datasets
(`scanpy.datasets`) or download models. Inputs come in with `write_file` (up
to 1 MiB per call), or from other AWS Quick tools whose results the model
writes into the sandbox. For enrichment analysis, write gene sets into the
sandbox as GMT files. Data leaves a sandbox only as tool results.

The VPC uses `10.0.0.0/22` and is not connected to anything. If you will
connect it to other networks, change `VPC_CIDR` in
`lib/constructs/isolated-network.ts` before the first deploy.

### Add or change an environment

1. Create `containers/sandbox/environments/<id>/pyproject.toml` from an
   existing one. The ID has at most 11 lowercase letters and digits, because
   Runtime names (`<projectName>_<id>`) are limited to 48 characters. Pin only
   the packages the environment needs, and fill in `[tool.code-sandbox]`:
   `parent`, `title`, `use-for`, optional `notes`, `programs` (each
   with a `check` command) and a `packages` entry (summary and import name)
   for every direct dependency. A shared layer that should not be deployed
   gets `deploy = false`.
2. Run `make lock` (needs access to PyPI). It resolves the layer against its
   parent's lock, so the parent's pins stay unchanged, and regenerates
   `lib/sandbox/catalog.json` and the table above. Packages without
   `linux/arm64` wheels cannot be installed, because the image has no
   compiler; pin a version with wheels.
3. Add an `env-<id>` stage to the Dockerfile, `FROM env-<parent>`, with the
   same `install-environment.sh` step.
4. Add an analysis for the environment to `ANALYSES` in
   `containers/sandbox/scripts/smoke_test.py`, and the environment to the
   table in `skills/scientific-computing-sandbox/SKILL.md`.
5. Run `make test-unit`, `make test-container SANDBOX_ENVIRONMENT=<id>` and
   `make image-report` (each image must stay under AgentCore Runtime's 2 GB
   limit on compressed image size, on platform version V1). Deploying adds
   the Runtime and its resource policy; then choose **Sync** on the AWS Quick
   connector.

To change an environment's packages, edit its `pyproject.toml` and run
`make lock`. Only that environment's image and those of its descendants
change on the next deploy.

## Prerequisites

- An AWS account and credentials for it, bootstrapped for CDK
  (`npx cdk bootstrap`).
- A Region where AgentCore Runtime supports VPC connectivity. The supported
  Availability Zone IDs per Region are in `AGENTCORE_AVAILABILITY_ZONE_IDS` in
  `lib/constructs/isolated-network.ts`; check the
  [AgentCore VPC documentation](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-vpc.html)
  for changes.
- Permission to create the service-linked role
  `AWSServiceRoleForBedrockAgentCoreNetwork` (`iam:CreateServiceLinkedRole`).
  The first VPC-mode runtime in the account creates it.
- Lambda concurrency: the tools Lambda reserves 50 concurrent executions by
  default, and Lambda keeps at least 100 of the account's concurrency
  unreserved. An account with a lower limit needs a smaller
  `toolsReservedConcurrency`, or `none`.
- Node.js 22 or later, npm, GNU Make and [uv](https://docs.astral.sh/uv/).
- A running container engine for deploys: Docker, or Finch with
  `CDK_DOCKER=finch`. The images are built for `linux/arm64`; on an x86 host
  the engine needs arm64 emulation, and builds are slower.
- An identity provider for AWS Quick sign-in; see
  [docs/authentication.md](../../../docs/authentication.md).

## Deploy

```bash
npm install
make deploy CDK_ARGS="-c jwtDiscoveryUrl=<discovery-url> -c jwtAllowedClients=<client-id>"
```

The first deploy builds seven images (the largest, `sctraj`, is about 1.7 GB
uncompressed and 0.5 GB compressed) and pushes them to the CDK assets
repository, so it takes a while. The `<projectName>-Gateway` stack outputs `GatewayUrl`.

| Context key | Default | Description |
| --- | --- | --- |
| `projectName` | `ls-scientific-computing-sandbox` | Prefix for stack IDs and resource names. 1-36 lowercase letters, digits or single hyphens, starting with a letter. The 36-character cap keeps `<projectName>-caller-identity-interceptor` within Lambda's 64 characters |
| `jwtDiscoveryUrl` | None (required) | Your identity provider's discovery URL |
| `jwtAllowedClients` | None | Allowed `client_id` claim values (comma-separated) |
| `jwtAllowedAudiences` | None | Allowed `aud` claim values (comma-separated) |
| `jwtAllowedScopes` | None | Scopes; the token must carry at least one (in its `scope` or `scp` claim) |
| `idleTimeoutSeconds` | `3600` | Seconds without calls before the Runtime stops a user's sandbox. 60-28800, at most `maxLifetimeSeconds` |
| `maxLifetimeSeconds` | `28800` | Maximum lifetime of a sandbox microVM in seconds. 60-28800 |
| `availabilityZoneIds` | The first two AgentCore-supported AZ IDs of the Region | 2-4 comma-separated Availability Zone IDs (not names, for example `use1-az1,use1-az2`) for the isolated subnets. Changing it after deployment replaces the subnets, which fails while AgentCore network interfaces use them |
| `toolsReservedConcurrency` | `50` | Reserved concurrency of the sandbox tools Lambda: the most tool calls that run at once across all users. A call can hold a slot for up to about 10 minutes. `none` reserves nothing |

Set `jwtAllowedClients`, `jwtAllowedAudiences`, or both; synthesis fails
otherwise. The interceptor checks the same values as the Gateway. Pass the
same `CDK_ARGS` to every later `make deploy` and `make destroy`, or put the
keys in the `context` block of `cdk.json`. In zsh, pass several `-c` flags as
literal arguments or through an array, not an unquoted string variable: zsh
does not split it, and synthesis rejects the resulting `projectName`.

## Connect to AWS Quick

Create an MCP connector in AWS Quick with the `GatewayUrl` output as the MCP
server endpoint and your identity provider's OAuth settings. The
[Cognito example](../../../docs/authentication.md#worked-example-amazon-cognito)
lists every field. Give the connector a description that helps AWS Quick
decide when to use it, for example "Remote Python sandboxes with scientific
packages for cheminformatics, medical imaging, variant files, RNA-seq,
multi-omics and single-cell analysis". AWS Quick should discover the nine
`sandbox___*` tools listed in [Tools](#tools).

Example prompts:

- "Calculate molecular weight, logP, TPSA and Lipinski violations for aspirin,
  ibuprofen and caffeine." (`chem`)
- "Here are 20 SMILES. Rank them by Tanimoto similarity to imatinib using
  Morgan fingerprints." (`chem`)
- "Here is a counts matrix and sample sheet. Which genes are differentially
  expressed between treated and control?" (`rnaseq`)
- "Run a preranked GSEA on this ranked gene list against the gene sets in this
  GMT file." (`multiomics`)
- "Cluster this small single-cell dataset with Leiden and plot a UMAP."
  (`sctraj`)
- "Which of these annotated variants are rare and likely pathogenic under
  ACMG criteria?" (`vcf`)
- "Which sandbox environments are available, and which would you use for RNA
  velocity?" (answered by `list_environments` without starting a sandbox)

## Test

```bash
make test-unit          # type-check, CDK and Lambda unit tests, Python server tests; no AWS or container engine
make test-integration   # tests against the deployed stacks; set PROJECT_NAME if you changed it
```

These targets need a container engine:

```bash
make test-container SANDBOX_ENVIRONMENT=chem   # build one image, run it on loopback, smoke-test it
make test-containers                           # every deployed environment, then the image report
make image-report                              # image sizes (under 2 GB compressed) and shared layers
```

The smoke test drives a container the way AgentCore Runtime does. It checks
package isolation, the read-only virtual environment without pip, the
scrubbed process environment, background jobs, `/ping`, every catalog package
at its catalog version, every catalog program, and a small analysis with the
environment's main packages. The container port is published on loopback
only.

The integration tests need AWS credentials for the deployed account,
including `lambda:InvokeFunction` on the tools Lambda. They check that the
runtimes deny your own credentials and that the Gateway rejects a request
without a token. By invoking the tools Lambda directly with two throwaway test
identities, they check that it fails closed without an identity, that
`list_environments` lists every environment, that a user's files persist
across calls, that another user and another environment get separate
sandboxes, that a sandbox has no internet access, that every environment
imports its catalog packages, and that `reset_sandbox` empties the sandbox.

To also test the Gateway, set `ACCESS_TOKEN` to an access token that your
identity provider issued to an allowed client, then run
`make test-integration`. The Gateway tests check the tool list, persistence
with a new MCP session for every call (as AWS Quick calls), and that the
Gateway ignores a caller header sent by the client.

To check persistence in AWS Quick itself:

1. In one conversation, ask: "Use the chem sandbox environment to write the
   current time to /workspace/marker.txt, then show get_sandbox_info."
2. In a later turn, ask it to read `marker.txt` and show `get_sandbox_info`
   again. The file exists and `sandbox_instance` is unchanged.
3. In a new conversation, ask for `get_sandbox_info` and a file listing. The
   `sandbox_instance` is the same and `marker.txt` is there, because the
   sandbox belongs to the user, not the conversation.
4. Ask it to call `reset_sandbox` for `chem`, then `get_sandbox_info`. The
   `sandbox_instance` is new and `/workspace` is empty.

## Cost

The main cost drivers:

- **AgentCore Runtime.** Billed per vCPU-hour and GB-hour of each active
  sandbox session. Memory is billed for the whole life of a microVM,
  including idle time, and CPU while it is active. A session lasts until 1
  hour without calls (`idleTimeoutSeconds`) or 8 hours at most
  (`maxLifetimeSeconds`), so each active user holds up to one microVM per
  environment they have used. `list_environments` starts none. The idle
  timeout is the main lever on idle cost. See
  [AgentCore pricing](https://aws.amazon.com/bedrock/agentcore/pricing/).
- **VPC interface endpoints.** Four interface endpoints (AgentCore, ECR API,
  ECR Docker, CloudWatch Logs) in two Availability Zones cost roughly USD 58
  a month in us-east-1 even with no traffic, plus a charge per GB processed.
  This figure is approximate and varies by Region. The S3 gateway endpoint is
  free.
- **AgentCore Gateway.** Charged per tool call and per search request.
- **Lambda.** The tools Lambda (512 MB, arm64) runs for the length of each
  sandbox call, up to about 10 minutes for a synchronous call. The
  interceptor (256 MB) runs briefly on every request.
- **Amazon ECR.** Storage of the seven images in the CDK assets repository.
  Shared layers are stored once.
- **CloudWatch Logs.** Lambda logs and VPC flow logs (rejected traffic only)
  are kept for 30 days. AgentCore creates the runtimes' log groups
  (`/aws/bedrock-agentcore/runtimes/<runtime>-*`) itself, with no expiry;
  set a retention period on them.
- **Route 53 Resolver DNS Firewall.** Charged per DNS query processed; small
  at this traffic.

## Security

- **cdk-nag.** `cdk synth` and `cdk deploy` run the cdk-nag AWS Solutions
  checks and fail on any finding without a documented suppression. Each
  suppression, next to its resource in `lib/`, gives the reason. Synthesis
  writes the results to `cdk.out/AwsSolutions-*-NagReport.csv`.
- **Inbound authentication.** The Gateway accepts only JWTs that your
  identity provider signed and that carry an allowed client ID or audience;
  synthesis fails if neither is set. The interceptor verifies every token
  again with the same settings, so a misconfigured authorizer cannot leave
  the sandbox without a verified identity. It fails closed if it cannot read
  the discovery document.
- **Per-user isolation.** Each user's sandbox is a separate microVM keyed by
  the verified `sub`. The interceptor always overwrites the caller header
  with the verified `sub`, and the tools Lambda takes identity only from that
  header, never from tool arguments. The `environment` argument only chooses
  among the caller's own sandboxes.
- **Who can reach a sandbox.** Each runtime's resource policy allows
  `InvokeAgentRuntime` and `StopRuntimeSession` only for the tools Lambda's
  role, and only through the sandbox VPC's AgentCore endpoint
  (`aws:SourceVpce`). It denies every other principal, so other IAM users and
  roles in the account cannot call a runtime around the Gateway, and the
  tools Lambda role's credentials do not work outside the VPC. The Gateway
  role can invoke only the interceptor and the tools Lambda, and only this
  Gateway can assume it (`aws:SourceArn` names the Gateway).
- **No internet egress from sandboxes.** See
  [Network isolation](#network-isolation): isolated subnets, VPC endpoints
  with restrictive policies, security groups and DNS Firewall.
- **Tools Lambda reserved concurrency** (`toolsReservedConcurrency`, default
  50) caps how many tool calls run at once, so long sandbox calls cannot use
  up the account's Lambda concurrency.
- **Known limitation: sandboxed code can read the Runtime execution role's
  credentials.** Code running in a sandbox can read the execution role's
  temporary credentials from the microVM's metadata endpoint
  (`169.254.169.254`). This was verified on a deployment. Anyone who can use a
  sandbox can print these credentials and use them from anywhere. Keep the
  role minimal. The stack creates it with only image pull, the runtime's own
  log groups, and CloudWatch metrics in the `bedrock-agentcore` namespace,
  and without the workload-identity actions the CDK `Runtime` construct adds
  by default. The image pull permission covers the whole CDK container assets
  repository of the account and Region, so a user could also pull the images
  of other CDK apps deployed there. Prefer a dedicated account, or a CDK
  bootstrap qualifier of its own.
- **Inside the microVM.** The server and the sandboxed code run as the same
  non-root user. Code runs with a minimal environment (no AWS or server
  variables), in its own process group, with the environment's own virtual
  environment, which root owns and which has no pip. Code can still stop or
  replace the server in its own sandbox, so the tools Lambda passes on only
  the error codes the server defines.
- **Packages.** Every package, including the build backend of packages
  published only as source distributions, is installed from a hash-checked
  lock. The base image is pinned by digest.
- **Logging.** The Lambdas log only the environment, tool name, outcome code
  and duration; the interceptor logs only the outcome and a fixed reason.
  Nothing logs tokens, the caller's `sub`, tool arguments, code, paths, file
  contents or output.

What to review before you use it:

- Every user who can sign in through your identity provider and use the AWS
  Quick connector can run arbitrary code in their own sandboxes. Restrict who
  can use the connector in your identity provider and in AWS Quick.
- Principals in the account with `lambda:InvokeFunction` or
  `lambda:UpdateFunctionCode` on the tools Lambda, or permission to change the
  runtimes' resource policies, can act as any user, because the tools Lambda
  trusts the caller in its invocation context. Deploy into a dedicated
  account, or restrict these permissions.
- Network isolation does not by itself make the accelerator suitable for
  regulated data such as PHI. Data reaches AWS Quick and its model through
  tool results. Check your organization's requirements and the HIPAA
  eligibility of each service first.
- Content the agent reads (uploaded files, sandbox output, other tools'
  results) can carry instructions. Such instructions could make the agent
  leave files or background jobs in a user's sandbox, which the user's later
  conversations share, or pass sandbox results to other tools the agent can
  use. Limit which other connectors and actions are available alongside this
  one, and use `reset_sandbox` if you suspect a sandbox was tampered with. The
  skill tells the agent to treat such content as data.
- If users need public scientific APIs, an egress allowlist (a NAT gateway
  behind AWS Network Firewall with a domain allowlist, plus matching DNS
  Firewall rules) is possible, but it reopens a path for data to leave.

## Clean up

```bash
make destroy CDK_ARGS="<the same CDK_ARGS you deployed with>"
```

This removes the three stacks. Some resources remain or need a retry:

- AgentCore keeps a deleted runtime's network interfaces for up to 8 hours,
  and they hold the subnets and the runtime security group. Deleting the
  `<projectName>-Network` stack can fail until they are gone; run
  `make destroy` again later.
- The first VPC-mode runtime in the account created the service-linked role
  `AWSServiceRoleForBedrockAgentCoreNetwork`. `make destroy` leaves it in
  place.
- The runtimes' log groups (`/aws/bedrock-agentcore/runtimes/<runtime>-*`) and
  the images in the CDK assets repository remain. Delete them if you no longer
  need them.

Delete the AWS Quick connector and any OAuth client you created for it
separately.
